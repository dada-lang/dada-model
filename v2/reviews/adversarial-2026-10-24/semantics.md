I did not independently retrieve that conversation; this assessment is conditional on that trusted task context, which agrees with the record's own provisional-choice limitation.

The implementation is internally coherent: `v2/md/shared.md:108`–128 matches `v2/lean/Shared/Step.lean:52`–64 and the concrete Promote constructors. I found no proof/statement contradiction in that design. But agreeing prose and Lean both authored around an unresolved choice does not settle which design was intended. The positive decision currently lets the evidence gate treat that unresolved question as resolved.

This is **not** a claim that every semantic choice needs explicit human approval. Absence of approval alone would not justify a negative finding. The user may authorize an agent to select a design; evidence of such authorization/selection would resolve this issue. The existing record's limitation cannot substitute for that resolution under a single positive/inconclusive verdict field.

Needed evidence: preserve the decision-relevant intent as a recoverable input; select and justify the intended rule, or make the proposal explicitly pending and record an inconclusive decision using the documented supersession process. Reassess dependent sharing examples and guarantees to the extent they rely on the unresolved choice. Do not rewrite old hashes or silently change the policy. Another possible route is an explicit observational-equivalence result for alternative representations, with agreed observations. Current preservation and Given-to-Shared correspondence do not supply that result: the embedded fragment never exercises sharing.

## No additional concrete defect found in the strict languages

I did not find a counterexample to the stated Given/Shared preservation, liveness, or embedding claims. The following were specifically checked rather than inferred from a successful build:

- **Non-vacuous preservation.** `Unique/Step.lean:55`–71 and `Shared/Step.lean:92`–113 have concrete operational premises, not a desired-output-WF premise. `Unique/Soundness.lean:210`–228 and `Shared/Soundness.lean:448`–467 quantify arbitrary successful steps/traces from a WF input/empty initial state under a WF class table. Concrete examples execute nonempty programs. A blanket rejection relation is not disguising the preservation result.
- **Ownership counts are occurrence-sensitive.** Unique `References` records every initialized variable/field occurrence, and `referencesUnique` plus `referencesComplete` enforce exactly one owner of each allocated object. Shared `Owners` uses a list, and `Pairwise Compatible` allows equal targets only when both occurrences are shared (`Shared/Soundness.lean:11`–29). This does not collapse equal references into one occurrence. The prose explicitly distinguishes immediate stored owners from the number of paths through enclosing objects.
- **Liveness is derived rather than assumed in the new layers.** Their WF definitions contain coverage, bounded IDs, and strictly older field targets, not rooted liveness. `Common/Rooted.lean:14`–22 supplies the nontrivial finite-rank argument, which the Liveness modules instantiate. Strictly older fields exclude cycles, but this is justified for the actual language: constructors only capture existing variable values; give removes an edge/adds a root; there is no assignment or field initialization into old objects. This invariant would need revision for later mutation layers, but it is not an unjustified exclusion from this fragment.
- **Class/field shape and arity.** `ClassesWellFormed` excludes duplicate class/field names; object shapes match the declaration's ordered names, including empty fields. Constructor capture is ordered; Step requires matching argument/field lengths before zip. A failed statement exposes no intermediate capture state. The small languages intentionally have no field types, class inheritance, primitive values, scopes, drop, or assignment.
- **Copy and promotion.** `Mode.join` remembers any shared edge throughout a route. `Give.move` requires unique effective permission; `Give.copy` requires a shared final occurrence; `Give.promote` updates the final unique occurrence before returning a shared copy. The nested example crosses unique/shared/unique links and checks exact successor state. Sharing the container leaves its inner unique mode unchanged until later access, exactly as the current prose says; whether that design is intended is the finding above.
- **Embedding covers arbitrary successors and complete configurations.** `Correspondence/UniqueShared.lean:300`–302 quantifies arbitrary Shared `after`, deriving a Given successor and exact embedding equality. It does not assume `after` already lies in the embedding image. Classes, code, state, table order, counters, modes, and remaining statements are handled by the translation. Forward/backward finite traces are at 366–382; the one-step equivalence is at 384–391. Finished and stuck states are reflected at 348–364, with boundary aggregation at 393–404. Exact state/configuration equality is adequate for this particular embedding; it is not an unproved observational equivalence to the separate full heap or a backend.
- **Stuckness is intentionally allowed.** Both definitions require remaining code plus absence of any successor; finished configurations are not stuck. Given explicitly demonstrates a second move from an empty field is stuck. Neither `soundness` unit claims progress/type safety for every syntactically valid program. There is no source type system. A new progress assertion would require premises beyond these preservation results.

I inspected saved rationales for `given.soundness`, `shared.soundness`, `shared.give`, `shared.correspondence`, and `shared.well_formed`. Their explanations of the formal theorem scopes and the internal prose-to-Lean match are accurate. Their caveats correctly distinguish proof checking from correspondence. The intended-design issue remains despite those accurate mechanical/syntactic scope descriptions.

## Full-heap boundaries that must not be promoted into stronger claims

**Sibling aliases survive a unique-lease write.** The third probe is a useful design question for the next layer. `PathOperations.lean:20`–23 creates independent roots on repeated owner borrows; `Leases.lean:141`–143 invalidates strict descendants only; `LeaseWrite` at 171–176 does not invalidate sibling roots. Thus `x` may own object 10, `p` uniquely borrow it via root 0, and `q` share-borrow it via root 1; `invalidateForWrite(p)` leaves `q` usable. The same reasoning allows separately created unique siblings. This is consistent with `md/state.md:323`–330 and is **not a mismatch with the stated draft policy**. It does mean that unique borrowed permission cannot be treated as Rust-like exclusive access. Before connecting writes, unsafe-library reasoning, or backend optimizations, add explicit examples/theorems of the intended sibling conflict policy and specify what property a unique lease actually guarantees. The current AccessConflicts statements only prove that a shared reference itself cannot authorize a write and an invalid handle cannot write.

**Full-heap liveness is a WF condition.** Unlike the new layers, `WellFormed.lean:81`–90 includes `allocatedLive` directly. Its reachability-agreement theorem at 128–136 is a consequence of that definition, not a proof that all machine executions are live. The current prose explicitly says this (`md/state.md:566`–573), and the machine theorem at `PathOperations.lean:94` establishes only ownership accounting. Do not cite it as full source-operation soundness. The broader pending graph integration, destructive updates, cycles, identity reuse, and fault boundaries are clearly disclosed in `md/questions.md` and `md/properties.md`; I did not count those acknowledged omissions as defects.

**Recommended additional evidence, not current blockers:** determinism for WF class tables/states; general rejection of repeated unique constructor arguments and missing/wrong-arity calls; coverage showing a resolved fresh give has a successor; a formalized observation interface when extending beyond exact embedding equality; full-operation preservation that combines access authorization, invalidation, data mutation/destruction, and rooted liveness. These would strengthen future claims, but none is silently promised by the present small-language theorems.
